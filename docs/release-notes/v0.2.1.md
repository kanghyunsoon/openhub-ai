# OpenHub AI v0.2.1

OpenHub AI v0.2.1 is a reliability and safety release. It does not add new tools. It makes interrupted operations recoverable, lets only one change run at a time, prepares Python tools before they are configured, limits what MCP servers see from your environment during checks, and stops new installs of Serena. The Verified Registry has **8 tools**. Nothing is installed or changed without a plan you approve, as before.

## Recovery and safe concurrent use

- **Interrupted operations can be recovered.** If an update, rollback or repair stops midway (for example the app was closed), the tool shows `interrupted-update`. Run `openhub lifecycle recover <toolId>` in a terminal, read the plan and approve it: OpenHub restores the previous entry only if the file still matches what it was writing, and never overwrites changes made by someone else. Use `--discard` when the configuration is already consistent and only the operation record is left.
- **Recovery is in the CLI only.** The desktop app does not recover by itself; its Installed view shows the exact command, how to get the CLI, and how to confirm the result afterwards.
- **One change at a time.** Install, update, rollback, repair and Health checks from the desktop app and the CLI take turns. A second operation stops with `OPERATION_IN_PROGRESS` and changes nothing, so a Version State record is no longer lost.
- **Health errors are compensated.** If a Health check cannot run during an update (for example the temporary folder cannot be created), the client configuration and Version State are restored. Health does not run when the tool's Registry entry cannot be read, and installs are refused while `~/.openhub/state/lifecycle.json` cannot be read.
- **Project selection.** Installing while another project is still being analyzed no longer writes into the new project, and using your home folder as the project is blocked instead of writing your user-level client files without the user-scope approval.

## Python tools (uvx)

- **Prepared before configuration.** A uvx tool pinned to exact versions is downloaded and checked after you approve and before any client file is written, using wheels only. The client configuration also runs it with `--no-build`, so a later start never builds source code that OpenHub did not review.
- **No source builds for pinned tools.** OpenHub prepares pinned uvx tools with wheels only and does not build Python packages from source. A pinned tool that needs a source build cannot be prepared and is not installed; nothing is written.
- **Unpinned uvx tools have no such guarantee.** A uvx tool whose package or `--with` dependencies are not pinned to exact versions is not prepared: it is downloaded when it first starts, and neither the client configuration nor Health and benchmark add `--no-build`. uv may then build a package from source that OpenHub did not review. In the Verified Registry the only uvx tool, Postgres MCP Pro, is pinned; this applies to uvx tools in custom Registries.
- **Postgres MCP Pro** is pinned to `postgres-mcp==0.3.0` with `mcp==1.30.0`. This fixes the v0.2.0 failure on a new machine, where the server could not start with the MCP SDK 2.x.
- **Serena: new installs stopped.** Serena needs a dependency (`proxy-tools`) that is only published as source code, and OpenHub cannot verify that build. Serena was removed from the Verified Registry. Install, update, rollback, Health, repair, adopt and benchmark refuse it with the reason, also when a custom Registry still contains it. An existing Serena entry and its Version State are kept and shown as withdrawn, an interrupted operation can still be recovered, and the README describes manual removal. Bringing Serena back is tracked in [#59](https://github.com/kanghyunsoon/openhub-ai/issues/59).

## Environment passed to MCP servers during checks

- Health checks and benchmarks now start MCP servers with an allowlisted environment: operating system and path variables, proxy and CA settings, the backend's own settings without their credentials, and only the variables the tool declares. Other variables in your environment, such as API keys and tokens, are not passed. Environment variables that change which code runs (for example `NODE_OPTIONS` or `PYTHONPATH`) are never passed.
- If a package index or registry setting in your environment cannot be passed unchanged (for example a URL that contains credentials), Health and benchmarks do not start the server and do not fall back to the public index. Put the setting and its credentials in `uv.toml` or `.npmrc` instead.

## Adopt and benchmark

- Adopt only registers an existing entry when its command and options match the reviewed Registry command. Benchmarks are not offered for tools that use an OpenHub tool configuration.

## Compatibility

- No breaking changes to CLI commands, client configuration files or the install and lifecycle plan formats. Settings and Version State from v0.2.0 remain valid; the desktop app and the CLI still read them.
- **Serena:** see above. Your existing Serena configuration is not changed or deleted.
- **Health environment:** a tool that only passed its Health check because it read an undeclared variable from your environment may now fail Health. How your client starts the server is not changed by this.
- **Custom Registries with uvx tools:** some uvx commands that v0.2.0 accepted are refused with `MANIFEST_COMMAND_REJECTED`, for two different reasons:
  - The package cannot be identified from the Manifest: URLs, paths, VCS sources, wheel or archive files, `--with-editable`, `--with-requirements`, and options that `uvx --help` in uv 0.12.3 does not list.
  - The package can be identified, but OpenHub's Prepare and update steps only handle options written with a space: `--from=…`, `--with=…`, `-wpackage`, `-w=package`, combined short flags such as `-qw`, comma-separated `--with` lists and `--`. Write them as `--from package==1.2.3 --with dependency==4.5.6`.

## Known limitations

- **Remaining limits of the environment allowlist.** It is not a sandbox: a server started by OpenHub still runs as your user and can read your files and use the network. The package source used when a tool was prepared is not permanently linked to later Health checks; the contents of `uv.toml` and `.npmrc` are not part of the approved plan; credentials hidden in a URL path cannot be detected. npm's own `node-options` setting (in `.npmrc`, or `npm_config_node_options` during npx Prepare) can still add Node.js options to the processes npm starts; OpenHub does not read it ([#63](https://github.com/kanghyunsoon/openhub-ai/issues/63)). When your client (Claude Code, Codex, Cursor) starts the server, the client decides the environment, not OpenHub.
- **Postgres MCP Pro on Windows:** in our measurement the first Health check after install took about 15 seconds of the 20 second limit (Linux: about 3 seconds). A slower machine or network may hit the limit; run the Health check again. Update and rollback to another version need that version's own startup time; an older version that starts too slowly fails Health and the previous configuration is restored.
- **Unpinned npx tools download during their first Health.** Memory MCP, Context7, Chrome DevTools MCP and Playwright MCP have no exact version in the Registry, so they are not prepared at install: the first Health check (like your client's first start) downloads the newest version inside the 20 second startup limit. We measured 8.4–10.4 seconds for Memory MCP on Windows with an empty npm cache, and one of four packaged Windows test runs hit the limit. Run the Health check again if it stops with `startup-timeout` ([#70](https://github.com/kanghyunsoon/openhub-ai/issues/70)).
- **Memory MCP stores memories inside the npx cache by default.** A new upstream version replaces that folder and deletes `memory.jsonl` in it, and an update or rollback to another version starts the server without the earlier memories. Copy `memory.jsonl` to a folder outside the npm cache and set `MEMORY_FILE_PATH` to its absolute path; OpenHub then refuses update and rollback for that entry (`config-drift`) instead of overwriting your setting ([#69](https://github.com/kanghyunsoon/openhub-ai/issues/69)).
- **Installing is not the same as a verified start.** Per-client start verification exists for **Kubernetes MCP Server only**; the other 7 tools have no per-client run record. The install plan shows the level for each client and operating system.

  Kubernetes MCP Server, started by the real client from the configuration OpenHub wrote:

  | Client | Windows | Linux | macOS |
  | --- | --- | --- | --- |
  | Claude Code | verified | verified | not verified (platform unverified) |
  | Codex | verified | verified | not verified (platform unverified) |
  | Cursor | not verified | not verified | not verified (platform unverified) |

- **Cursor:** OpenHub writes Cursor configuration, but starting tools from Cursor is **not verified** on any platform.
- **Claude Code:** project scope only; OpenHub does not write the Claude Code user configuration.
- **macOS:** no official artifact and nothing is verified on macOS (platform-unverified). Building from source is not blocked.
- **Kubernetes MCP Server:** only version 0.0.67 is allowed. Other versions are blocked until reviewed.
- **Verified Registry size:** 8 tools. The earlier target of 25–40 verified tools is **not met** and stays carried over; unverified tools are not added to reach a number.
- **Windows installer:** the NSIS installer has no code signature. How Windows SmartScreen or Smart App Control reacts to it has **not been observed**; a warning may appear.
- **Linux AppImage:** release testing on CI runners without FUSE extracts the AppImage (`--appimage-extract`) and starts the extracted app. Starting the AppImage file directly through FUSE is not part of release testing.

### Windows x64

Download:

`OpenHub-AI-Setup-0.2.1-x64.exe`

The Windows installer is currently **unsigned**. Windows SmartScreen or Smart App Control may display a warning.

### Linux x64

Download:

`OpenHub-AI-0.2.1-x86_64.AppImage`

### CLI

Download:

`openhub-ai-0.2.1.tgz`

Install it with:

~~~sh
npm install -g ./openhub-ai-0.2.1.tgz
openhub --version
openhub lifecycle status --project ./my-project
~~~

Node.js 24.15 or later is required.

## Security and Verification

This release includes:

- `SHA256SUMS` for release artifact integrity. It shows that your download matches the published file; it does not prove who built it and is not a malware scan.
- CycloneDX 1.7 dependency SBOMs
- Windows native/runtime artifact SBOM
- Electron runtime provenance verification
- License and third-party notice validation
- CLI, Windows, and Linux smoke tests

The packaged desktop applications use Electron 44.5.1.
