# v0.2.1 Registry verification matrix

Measured on 2026-10-11 for the 9 Manifests in `registry/`. Each tool was started with its Manifest launch command and driven through a real MCP stdio handshake (`initialize`, `notifications/initialized`, `tools/list`). "Cold" uses a new, empty npm or uv cache; "warm" is the second start with that cache. No real credentials, clusters or databases were used.

- Windows: Windows 11, local machine. npx tools were started as `node <npx-cli.js> …` (the same launcher OpenHub uses for Health on Windows). uv 0.12.3.
- Linux: Docker containers on the same machine. npx tools in `node:22-bookworm-slim`, uvx tools in `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` (uv 0.9.30).
- Environment values were fake: `DATABASE_URI=postgresql://probe:probe@127.0.0.1:1/probe` (unreachable), a synthetic kubeconfig pointing at `https://127.0.0.1:1` with a fake token, `GITHUB_PERSONAL_ACCESS_TOKEN=fake-not-a-token`. Kubernetes used the reviewed policy file from `KUBERNETES_TOOL_CONFIG`.
- These numbers are single measurements on one machine and network. They show which tools are close to the 20 s Health startup limit; they are not performance guarantees.

## Findings

### postgres-mcp fails on an empty uv cache (fixed in v0.2.1)

`postgres-mcp` 0.3.0 depends on `mcp[cli]>=1.5.0` with no upper bound. On an empty uv cache uv picks `mcp` 2.3.0, and the server exits at import:

```
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer …
```

Same result on Windows and Linux, cold and warm. Users who already had an older uv cache entry may not see it until the cache refreshes.

The v0.2.1 Manifest keeps `postgres-mcp` unpinned and pins only the MCP SDK:

```
uvx --from postgres-mcp --with mcp==1.30.0 postgres-mcp --access-mode=restricted
```

The artifact is still the `--from` value (`postgres-mcp`), so identity, floating-artifact approval and `update` behave as before; `update` replaces only that token (for example `--from postgres-mcp==0.3.0`) and keeps `--with mcp==1.30.0`. `mcp==1.30.0` is the newest 1.x release on PyPI at the time of writing. When a future `postgres-mcp` release requires `mcp` 2.x, this pin must be reviewed again.

### Tools close to or over the 20 s Health startup limit on a cold cache

- serena on Windows: 21.9 s cold (over the limit), 5.8 s warm. On Linux 8.5 s cold.
- context7 and chrome-devtools-mcp on Windows: 14–16 s cold.
- postgres-mcp: dominated by the database connect wait (see above).
- mongodb-mcp-server: 75 s cold on Windows, but it is an exact-version npx tool, so OpenHub's npx Prepare downloads it before Health. Health then sees the warm time.

uvx tools have no Prepare step, so a first Health right after install or update can time out on a slow machine. A uvx Prepare would install Python packages before Health, and installing a Python package can run build code, so it needs its own approval design. It is proposed as a decision, not implemented in v0.2.1.

## Not covered

- macOS, Cursor launches, and real credentials or services.
- github-mcp-server on Linux and a true cold Docker pull.
- Tools beyond `tools/list` (no `tools/call`).
