Measured on 2026-10-11 for the 9 Manifests that were in `registry/` at the time. Each tool was started with its Manifest launch command and driven through a real MCP stdio handshake (`initialize`, `notifications/initialized`, `tools/list`). "Cold" uses a new, empty npm or uv cache; "warm" is the second start with that cache. No real credentials, clusters or databases were used.

v0.2.1 stops new Serena installs (see "Serena in v0.2.1" below), so the v0.2.1 Registry has 8 tools. The serena rows are kept as measurements of the v0.2.0 Manifest.

- Windows: Windows 11, local machine. npx tools were started as `node <npx-cli.js> …` (the same launcher OpenHub uses for Health on Windows). uv 0.12.3.
- Linux: Docker containers on the same machine. npx tools in `node:22-bookworm-slim`, uvx tools in `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` (uv 0.9.30).

Kubernetes used the reviewed policy file from `KUBERNETES_TOOL_CONFIG`.
- These numbers are single measurements on one machine and network. They show which tools are close to the 20 s Health startup limit; they are not performance guarantees.

## postgres-mcp in v0.2.1 (final, on main with #45 and #46)

The v0.2.1 Manifest pins postgres-mcp to reviewed exact versions, which turns on uvx Prepare (wheels only, #45, design `docs/specs/uvx-prepare.md`):

```
uvx --from postgres-mcp==0.3.0 --with mcp==1.30.0 postgres-mcp --access-mode=restricted
```

OpenHub writes the client entry with `--no-build` in front (`uvx --no-build --from postgres-mcp==0.3.0 …`), so a client that later starts the server cannot build source code that was not reviewed. Health starts the server with the allowlisted environment and the package-source check from #46.

The Health environment source is the real process environment (the same path as the CLI and Desktop). A new, empty `UV_CACHE_DIR`; the throwaway test PostgreSQL from the section below; a pre-existing `notes` entry in `.mcp.json` in every case. Windows: local Windows 11, uv 0.12.3. ## Serena in v0.2.1: new installs stopped

Serena (`serena-agent`) needs `proxy-tools 0.1.0`, which has no wheel on PyPI. v0.2.1 does not build source code during Prepare (#45), so Serena cannot be prepared safely. v0.2.1 therefore removes `registry/coding-agent/serena.yaml` and its catalog entry; the Manifest schema is unchanged. Bringing Serena back is tracked in #59.

`packages/core/src/registry/withdrawn.ts` keeps a fixed list with the tool ID, the version that stopped it, the reason and the Issue link. It has no command and no execution path. It is used only to give a clear answer:

- The block is decided in Core when a plan is built (`resolveRegistryTool`, `withdrawnManifestError`), not by Registry validation. install, Adopt, update, rollback, Health, repair, Benchmark and Pinokio plans for Serena return `TOOL_WITHDRAWN` (not `TOOL_NOT_FOUND`) with the reason and #59. Nothing is run or written.
- This holds even when a user-defined Registry or a Manifest passed directly (Pinokio) contains Serena. A Manifest with another name is treated as Serena when its GitHub repository (`oraios/serena`), canonical MCP alias (`serena`), or a PyPI package in its install information (`serena-agent`, PEP 503 normalized, or the `github.com/oraios/serena` git URL) matches. These identity values are used only to block; they are not commands.
- The CLI no longer stops at "not in the Registry" before Core: `install`, `install --backend pinokio`, `update`, `rollback`, `lifecycle health` and `lifecycle repair` print the reason and #59 (exit 2). The Desktop Pinokio preview shows the same reason in English or Korean.
- Serena is not a recommendation candidate, even when a user Registry contains it, so it is never shown as installable. An installed Serena entry is still identified.
- `lifecycle status` still reads and shows an existing Serena entry, with a "withdrawn" line and #59.
- The existing client entry and Version State are not deleted. Manual removal is described in the README.
- Journal recovery does not need the Manifest: an interrupted Serena update is restored by `lifecycle recover` (test `packages/core/test/registry/v021-serena-withdrawn.test.ts`).
- Registry validation also fails if a Manifest for a withdrawn tool comes back without first removing it from the list, but safety does not depend on it.
- Limit: identity matching covers the values above. A Manifest that installs the same code under an unrelated name, package and repository (for example a fork published under another name) is not recognized as Serena.

Earlier result kept for the record (2026-10-11, with the then-planned `source-build-reviewed` Prepare): one of six Serena installs on Windows failed in Prepare with `STEP_FAILED` after 11.4 s; its uv output was not captured and the cause is unknown. Nothing was written. Five later runs, each with a new empty cache, succeeded. This is no longer a v0.2.1 path, but the cause is still not known.

## Findings

### postgres-mcp fails on an empty uv cache (fixed in v0.2.1)

`postgres-mcp` 0.3.0 depends on `mcp[cli]>=1.5.0` with no upper bound. On an empty uv cache uv picks `mcp` 2.3.0, and the server exits at import:

```
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer …
```

Same result on Windows and Linux, cold and warm. Users who already had an older uv cache entry may not see it until the cache refreshes.

The v0.2.1 Manifest pins both packages to reviewed exact versions:

```
uvx --from postgres-mcp==0.3.0 --with mcp==1.30.0 postgres-mcp --access-mode=restricted
```

The artifact is the `--from` value (`postgres-mcp==0.3.0`), so the install plan has no floating-artifact approval and gets a uvx Prepare step. `update` replaces only that token (with an exact `--to` version; the Desktop update targets the Manifest version) and keeps `--with mcp==1.30.0`. Adopt accepts only the reviewed version. `mcp==1.30.0` is the newest 1.x release on PyPI at the time of writing. When a future `postgres-mcp` release requires `mcp` 2.x, this pin must be reviewed again.

### Tools close to or over the 20 s Health startup limit on a cold cache

- serena on Windows: 21.9 s cold (over the limit), 5.8 s warm. On Linux 8.5 s cold.
- context7 and chrome-devtools-mcp on Windows: 14–16 s cold.
- postgres-mcp: on Windows the first Health after install exceeds 20 s (see the real OpenHub measurement above); on Linux it is about 9 s.
- mongodb-mcp-server: 75 s cold on Windows, but it is an exact-version npx tool, so OpenHub's npx Prepare downloads it before Health. Health then sees the warm time.

With the pinned v0.2.1 Manifest, postgres-mcp is prepared before the config write (#45), and the measured first Health is within the limit on both systems (section above). Serena is no longer installable in v0.2.1.
