# v0.2.1 packaged RC: lifecycle checks on Context7

Status: proposal (Draft PR). Related: [#69](https://github.com/kanghyunsoon/openhub-ai/issues/69) (Memory MCP withdrawal), [#70](https://github.com/kanghyunsoon/openhub-ai/issues/70) (unpinned npx first start).

## Problem

v0.2.1 withdraws Memory MCP (#69): it leaves the bundled Registry, and Core refuses any plan for the npm package `@modelcontextprotocol/server-memory`, also from a custom Registry. The packaged RC harness (`scripts/rc/packaged-rc.mjs`) used Memory MCP from the bundled Registry for its install, user-scope, Health, exact-version update, rollback, Korean-dialog and Health-failure-compensation checks. On v0.2.1 artifacts those checks would fail for a reason that says nothing about the product.

## Constraints

- No test Registry inside the release artifacts or the packaged app (the harness keeps deleting `OPENHUB_REGISTRY` before every launch). The RC checks what users get.
- No check is removed, skipped or turned into NOT-RUN. The verdict rules (`check-rc-result.mjs`, fail-closed) are unchanged.
- The Health limits (startup 20 s) are unchanged. The npm cache is not warmed before the first Health.

## Options

| Option | Result |
| --- | --- |
| A. Another bundled Registry tool with real npm (chosen) | Same checks on a supported tool; works on v0.2.0 and v0.2.1 artifacts |
| B. A test Registry for the packaged app | Rejected: it proves a path users do not have; already rejected in [desktop-exact-version-update.md](desktop-exact-version-update.md) |
| C. Pinned tools only (Kubernetes MCP Server 0.0.67, MongoDB MCP Server 3.0.5) | Rejected: Kubernetes MCP Server only accepts its reviewed version (tool config policy), and MongoDB MCP Server needs a database for meaningful checks |

The Installed view's exact-version input is open for every consistent npx entry, pinned or not (`canChooseVersion`); only tools with a reviewed tool config (Kubernetes MCP Server) are limited to their reviewed version. Context7 is the smallest candidate (13 dependencies, no browser), needs no credential (`CONTEXT7_API_KEY` is optional) and answers initialize and tools/list without its web service. (An earlier draft of this page said only unpinned tools accept another exact version; that was wrong and is corrected here.)

Versions: V1 `4.1.0` (npm, 2026-09-11) and V2 `4.1.1` (2026-09-14). Both are older than npm's 72-hour unpublish window and declare `node >=20.18.1`.

## What changes in the harness

- `TOOL_ID`/`TOOL_ALIAS` `context7`, `TOOL_PKG` `@upstash/context7-mcp`, `TOOL_V1`/`TOOL_V2` replace the Memory MCP constants.
- The synthetic project's `package.json` gains a `react` dependency so that Context7 is recommended (library-docs gap). The Kubernetes files stay. Checked with the CLI on the current Registry: Chrome DevTools MCP, Playwright MCP, Kubernetes MCP Server and Context7 are recommended (with Memory MCP as well on the v0.2.0 Registry).
- The synthetic Health-failure injector ends only processes whose arguments contain `context7-mcp` and not `--package=` (npx Prepare), as before for the memory server.
- Step 8's evidence key is `npxTool` (with `toolId`) instead of `memory`.

## Update: Context7 pinned to V1 (#70)

The bundled Registry now pins Context7 to `@upstash/context7-mcp@4.1.0` (= `TOOL_V1`), so it is prepared after approval and before the configuration is written. The v0.2.0 dry-run artifacts used by the PR self-test still carry the unpinned Manifest; RC runs that matter for v0.2.1 use a new dry-run built from the new HEAD.

What changes in the harness and why:

| Check | Before (unpinned Manifest) | After (pinned Manifest) |
| --- | --- | --- |
| 7 Approved project install | launch-on-demand install, no preparation | install shows the `--package=@upstash/context7-mcp@4.1.0` preparation in the approval dialog and prepares V1 |
| 8 Real MCP Health | first Health downloads the newest version inside the 20 s limit | first Health starts the prepared V1 (no download) |
| 9 V1 | exact update "unpinned → V1" with npx Prepare | V1 comes from the install. New required check `install-prepared-exact-version`: the install dialog showed the V1 preparation, the npx cache entry for V1 is complete, client args and Version State (requested and resolved) are V1, and step 8's Health of V1 succeeded |
| 9 V1 → V2 | exact update with Prepare and Health | unchanged |
| 10 Rollback to V1, Health | unchanged | unchanged |
| health-failure-compensation | update to V2 with an injected failure, restored | unchanged |

No check was removed, skipped or turned into NOT-RUN; one required check was added on both OSes (`check-rc-result.mjs`). The "unpinned → pinned" transition that existing users go through is not part of the packaged RC (the bundled Registry no longer has an unpinned Context7). It is covered by `packages/core/test/lifecycle/v021-context7-pin.test.ts`: plan without writes, approved update with Prepare and Health, Prepare failure, Health failure compensation, PLAN_STALE after an external change. The real npm/npx path is covered by `npx-prepare.e2e` and `npx-lifecycle-real.e2e` (OPENHUB_E2E), which now use the Registry Manifest unchanged.

## Risk

- **First Health of an unpinned npx tool (before the pin).** Before Context7 was pinned, step 8 ran the first Health right after a launch-on-demand install, so it downloads the package within the 20 s startup limit (#70). Context7 is larger than Memory MCP: on a Windows development PC with an empty npm cache its first start took about 15.8 s (Memory MCP: 8.4–10.4 s), on Linux 6.4–8.2 s, and 0.73 s once prepared. Memory MCP already hit the limit in one of four packaged Windows RC runs. If step 8 stops with `startup-timeout`, that is a product result for #70, not a harness defect. The harness is not changed to retry or to warm the cache; how to treat such a result is a maintainer decision.
- **Upstream changes.** With the pin, every RC step uses the fixed V1/V2. Chrome DevTools MCP and Playwright MCP stay unpinned and their first Health is not part of the RC (#70 remains open for them).
- **PR self-test.** `rc-packaged.yml` runs this harness on pull requests that change it, against the fixed v0.2.0 dry-run artifacts (run 38115277816). That run validates the harness, not a v0.2.1 release candidate.
