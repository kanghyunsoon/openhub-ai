# v0.2.0 specification

Status: P0-1 in progress (`feat/stack-coverage`); P0-2 and P0-3 planned.
Baseline: v0.1.1 (`95ed290`). Roadmap: [docs/roadmap.md](../roadmap.md).

Labels: **Fact**, **Decision**, **Proposal**, **Open Question**.

## Target users

Developers who use Claude Code, Codex or Cursor on real projects and want MCP servers that fit the project, with clear reasons and a safe install path. v0.2.0 adds backend (Node.js, Go), test-heavy, game (Unity, Unreal Engine) and Kubernetes projects to the shapes OpenHub understands, and English-speaking desktop users.

## Problems (Fact, observed on v0.1.1)

1. Go projects: nothing recognized, nothing recommended.
2. Unity and Unreal Engine projects: only C# or C++ recognized.
3. Express, NestJS, Jest, Vitest, pytest and Playwright not recognized.
4. An empty recommendation list gave no reason.
5. The Verified Registry has 7 tools, so many real needs have no candidate.
6. The desktop app is Korean only.

Related tools, as observed while planning (Fact, not a comparison of quality): the official MCP Registry publishes server metadata (its license was moving from MIT to Apache-2.0); mcpm.sh is an MCP package manager CLI; Smithery provides a CLI and hosted registry. OpenHub's difference is project analysis plus an approval-gated lifecycle, not catalog size.

## P0-2 Registry expansion

Goal (Decision D-v2-2): 25-40 verified tools. Proposal: add them in reviewable batches of 5-8 Manifests per pull request, each batch with its verification record.

### Verification criteria (Decision)

A tool enters the Verified Registry only when all of these are checked and recorded:

1. Real open-source project with a public upstream repository.
2. License identified (SPDX); no license or a license that forbids redistribution of the launch command is a rejection.
3. Maintained: not archived, recent commits or releases.
4. Install method works with an existing backend (npx, uvx, Docker), with an exact package or image name confirmed in the registry it comes from. Other methods stay candidates.
5. Supported clients checked against the tool's own documentation.
6. Required permissions and environment variable names recorded (names only, never values).
7. Not a duplicate of an existing Manifest or alias.
8. Manifest validation passes (`pnpm registry:validate`).
9. Supply-chain review: package publisher matches upstream, no install scripts that fetch arbitrary code, no obfuscated code in the published artifact.
10. Capabilities assigned from the tool's real functions, using taxonomy IDs only.

Stars are context, not evidence of safety.

## P0-3 Desktop UX

Design only in this phase (Proposal).

| ID | Requirement |
| --- | --- |
| UX-1 | English is the default UI language; Korean is selectable in settings. |
| UX-2 | The choice is stored in a new desktop settings file and restored on restart. (Fact: v0.1.x has no desktop settings file.) |
| UX-3 | Users of the Korean-only build keep Korean after upgrading. Because v0.1.x stored no language setting, the first v0.2.0 launch with no saved language chooses Korean when earlier OpenHub data already exists (`~/.openhub/`, written by v0.1.x lifecycle and metadata features), otherwise English, and saves the result once. The user can change it at any time. |
| UX-4 | Install target scope (project or user) and AI client can be chosen in the install dialog; the plan preview shows the exact config file that will change. |
| UX-5 | FOR YOU shows the empty-result reason from `diagnoseRecommendation` and, for needs without a verified tool, says so instead of showing nothing. |
| UX-6 | Plan previews explain each approval requirement in plain language. |
| UX-7 | The approval flow is unchanged: native dialog, plan digest, `PLAN_STALE` on change. |

Design notes: strings move to per-language message tables in the renderer; core and CLI keep their current output in this phase (CLI language is an Open Question). Product names, IDs, paths and command lines are never translated.

## Compatibility (Decision)

- RecommendationReport stays v1. Only `taxonomyVersion` changes (1 → 2). Old reports are rejected, never reinterpreted.
- ProjectProfile keeps its fields. New IDs appear in existing lists, and the detector list gains `kubernetes`.
- Registry Manifest v1 is unchanged; existing Manifests validate.
- InstallPlan v1, LifecyclePlan v1 and LifecycleStateFile v1 are unchanged (goldens).
- Recommendation results can change for projects that use the new technologies; the before/after table documents it.
- npx Prepare (exact-version npx packages are downloaded after approval and before client config writes; InstallPlan v1 and LifecyclePlan v1 gain an additive `npx` run step): [npx-prepare.md](npx-prepare.md).

## Test and E2E plan

- Unit and fixture tests for every SC criterion (A detection, B needs, C Registry, D recommendations), including negative and malformed cases.
- Golden updates are allowed only for the documented reasons; any other golden change is a regression.
- CLI E2E: `openhub project scan` and `openhub project recommend` on Go, Express, NestJS, Unity, Unreal Engine and React + Spring fixtures, compared with v0.1.1.
- Full gates: tests, typecheck (including scripts), desktop build, `registry:validate`, `notices:check`, gitleaks, CI and CodeQL.

## Non-functional requirements

- Determinism: same input, same bytes.
- Safety: files are read, never executed; YAML parsing caps aliases and documents; evidence values are bounded and pattern-checked; regular expressions are linear (no new ReDoS patterns).
- Privacy: no network calls during analysis or recommendation.

## Out of scope for v0.2.0

- Automatic installation or updates without approval.
- Installing unverified discovery candidates.
- LLM-based detection or ranking.
- Installing editor plugins inside Unity or Unreal Engine.
- Code signing and a macOS release artifact.
- CLI translation.

## Open Questions

- Game-editor MCP servers need a plugin inside the editor. Should OpenHub list them with a manual step, or keep them as candidates?
- Should CLI output follow the desktop language setting, or stay as is until a later version?
- UX-3 alternative: use the OS locale instead of existing OpenHub data to pick the first language. Existing data is closer to "existing user"; the OS locale also helps new Korean users. Which one, or both?
- Which capability IDs should P0-2 add for Terraform, Redis, observability and design tools, given that each addition raises the taxonomy version?
