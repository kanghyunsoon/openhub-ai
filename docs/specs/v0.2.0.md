# v0.2.0 specification

Status: P0-1 in progress (`feat/stack-coverage`); P0-2 and P0-3 planned.
Baseline: v0.1.1 (`95ed290`). Roadmap: [docs/roadmap.md](../roadmap.md).

Labels: **Fact**, **Decision**, **Proposal**, **Open Question**.

## Target users

Developers who use Claude Code, Codex or Cursor on real projects and want MCP servers that fit the project, with clear reasons and a safe install path. v0.2.0 adds backend (Node.js, Go), test-heavy, game (Unity, Unreal Engine) and Kubernetes projects to the shapes OpenHub understands, and English-speaking desktop users.

## Problems (Fact, observed on v0.1.1)

1. Go projects: nothing recognized, nothing recommended.
2. Unity and Unreal Engine projects: only C# or C++ recognized.
3. Express, NestJS, Jest, Vitest, pytest and Playwright not recognized.
4. An empty recommendation list gave no reason.
5. The Verified Registry has 7 tools, so many real needs have no candidate.
6. The desktop app is Korean only.

Related tools, as observed while planning (Fact, not a comparison of quality): the official MCP Registry publishes server metadata (its license was moving from MIT to Apache-2.0); mcpm.sh is an MCP package manager CLI; Smithery provides a CLI and hosted registry. OpenHub's difference is project analysis plus an approval-gated lifecycle, not catalog size.

## Decisions

| ID | Decision |
| --- | --- |
| D-v2-1 | Taxonomy may grow. Changing the capability or tech ID tables raises `taxonomyVersion` to 2. RecommendationReport stays `schemaVersion: 1`. No v1 ID is removed or changes meaning; new IDs are appended without duplicates. Reports with `taxonomyVersion: 1` are rejected and must be regenerated, never silently accepted. Until v0.2.0 ships, further additions stay in version 2; after release, any change raises the version. |
| D-v2-2 | Verified Registry target is 25-40 tools, reached only with tools that meet every criterion in [P0-2](#p0-2-registry-expansion). Unverified tools are never added to reach the number. Registry growth ships in P0-2, not in the P0-1 pull request. |
| D-v2-3 | Desktop default language is English; Korean stays available. The user can switch, the choice persists across restarts, and existing Korean users keep Korean. Done in P0-3, not mixed into P0-1. |
| D-v2-4 | Planning documents live in the public `docs/` folder (`docs/roadmap.md`, `docs/specs/*.md`). Each fact is written once and linked from elsewhere. Nothing depends on private repositories. |

## P0-1 Stack coverage

Details, evidence rules, Need Rules and the before/after table: [stack-coverage.md](stack-coverage.md).

| ID | Requirement |
| --- | --- |
| SC-1 | Recognize Go, Express, NestJS, Jest, Vitest, pytest, Playwright, Unity, Unreal Engine and Kubernetes from project files or declared dependencies only. |
| SC-2 | Do not report Unity for plain C#, Unreal Engine for plain C++, or any technology from README text. |
| SC-3 | Malformed manifests never fail a scan and never produce strong evidence. |
| SC-4 | Taxonomy v2 adds capabilities and tech IDs without changing v1 IDs; NR-01 to NR-08 unchanged; new rules from NR-09. |
| SC-5 | Recognized technologies reach recommendations through Need Rules, and only verified Registry tools are recommended. |
| SC-6 | When there are no recommendations, the user sees which layer is empty: stack, Need Rule, verified tool, compatibility, or already satisfied. |
| SC-7 | Existing contracts stay compatible: RecommendationReport v1, ProjectProfile fields, Registry Manifest v1, InstallPlan and LifecyclePlan goldens. |

Acceptance criteria (each maps to tests in `packages/core/test/stack-coverage.test.ts` unless noted):

- SC-1.1 Each new technology is recognized in its fixture with the exact evidence listed in stack-coverage.md.
- SC-1.2 A monorepo with web, API, worker and deploy folders reports every technology once, with evidence from each package.
- SC-2.1 `csharp-console` has no frameworks; `cpp-cmake` has no frameworks; `readme-mentions` has no languages, frameworks, databases or infrastructure.
- SC-3.1 `malformed-stack`: broken `.uproject` and `go.mod` give file-presence evidence with confidence below 0.9; broken Unity files and invalid Kubernetes YAML give nothing.
- SC-4.1 `TAXONOMY_VERSION` is 2; the first 14 capabilities and their labels equal v1; the two new capabilities are appended; v1 tech IDs keep their positions; no duplicates.
- SC-4.2 NR-01 to NR-08 are byte-identical to v1; new rules are NR-09 to NR-13 and use only known tech IDs.
- SC-4.3 All existing Registry Manifests validate under v2.
- SC-4.4 A report with `taxonomyVersion: 1` fails schema validation at `generatedFrom.taxonomyVersion`.
- SC-5.1 Go recommends Serena only; Express recommends Postgres MCP, Serena and Context7; NestJS recommends Serena and Context7.
- SC-5.2 Unity and Unreal Engine produce a high-priority `game-engine-editor` need with no candidates and a `no-candidate` reason, and recommend nothing beyond the existing C# or C++ code-navigation tool.
- SC-5.3 A Playwright project's `e2e-testing` need cites Playwright as a source and Playwright MCP is recommended.
- SC-5.4 The React + Spring monorepo recommendation list is unchanged.
- SC-6.1 `diagnoseRecommendation` returns `no-stack-detected` for README-only projects, `no-verified-tool` for Kubernetes-only projects, and lists `jest` and `pytest` as recognized but not mapped.
- SC-6.2 `openhub project recommend` prints the empty-result reason and the unmapped technologies; `--json` has no new fields (`apps/cli/test/recommend-diagnosis.test.ts`).
- SC-7.1 Full test suite passes; InstallPlan v1, LifecyclePlan v1 and LifecycleStateFile v1 goldens are unchanged; the RecommendationReport schema digest changes only through the `taxonomyVersion` literal.

Technical changes (Fact): new tech rules with an optional `configFiles` field; game-engine detection in the frameworks detector; Go in the language detector; a new `kubernetes` detector; taxonomy v2; NR-09 to NR-13; `diagnoseRecommendation` in `@openhub/core`; CLI output for the diagnosis.

## P0-2 Registry expansion

Criteria, verification method, per-tool records, candidates and batch results: [registry-expansion.md](registry-expansion.md).

| ID | Requirement |
| --- | --- |
| RX-1 | Every criterion is checked and recorded per tool before its Manifest is merged. |
| RX-2 | Each batch passes `registry:validate`, the full test suite and the OpenHub sandbox Health Check for its tools. |
| RX-3 | No Manifest without a verification record; failed tools are recorded with the reason and not added. |
| RX-4 | Capabilities outside the taxonomy are added only for tools being registered; before v0.2.0 ships they stay in `taxonomyVersion` 2. |
| RX-5 | Tests do not hard-code the Registry size; contract goldens may change only through Registry-derived digests and entries of the new tools. |

Status (Fact): batch 1 registered `kubernetes-mcp-server` (8 tools in total); MongoDB MCP Server is deferred; game-editor tools stay candidates.

## P0-3 Desktop UX

Design only in this phase (Proposal).

| ID | Requirement |
| --- | --- |
| UX-1 | English is the default UI language; Korean is selectable in settings. |
| UX-2 | The choice is stored in a new desktop settings file and restored on restart. (Fact: v0.1.x has no desktop settings file.) |
| UX-3 | First launch (Decision): a saved language setting wins; with none, the OS UI language decides: any `ko` locale (for example `ko`, `ko-KR`) starts in Korean, everything else in English. The result is saved and kept across restarts; the user can change it at any time. The existence of `~/.openhub/` is not treated as evidence of a Korean desktop user (it is also written by the CLI). Whether earlier desktop users can be identified at all is investigated separately. |
| UX-4 | Install target scope (project or user) and AI client can be chosen in the install dialog; the plan preview shows the exact config file that will change. |
| UX-5 | FOR YOU shows the empty-result reason from `diagnoseRecommendation` and, for needs without a verified tool, says so instead of showing nothing. |
| UX-6 | Plan previews explain each approval requirement in plain language. |
| UX-7 | The approval flow is unchanged: native dialog, plan digest, `PLAN_STALE` on change. |

Design notes: strings move to per-language message tables in the renderer. Product names, IDs, paths and command lines are never translated.

CLI (Decision): v0.2.0 keeps the current CLI output language. The CLI does not read the desktop language setting. CLI translation is considered in a later version.

## Compatibility (Decision)

- RecommendationReport stays v1. Only `taxonomyVersion` changes (1 → 2). Old reports are rejected, never reinterpreted.
- ProjectProfile keeps its fields. New IDs appear in existing lists, and the detector list gains `kubernetes`.
- Registry Manifest v1 is unchanged; existing Manifests validate.
- InstallPlan v1, LifecyclePlan v1 and LifecycleStateFile v1 are unchanged (goldens).
- Recommendation results can change for projects that use the new technologies; the before/after table documents it.

## Test and E2E plan

- Unit and fixture tests for every SC criterion (A detection, B needs, C Registry, D recommendations), including negative and malformed cases.
- Golden updates are allowed only for the documented reasons; any other golden change is a regression.
- CLI E2E: `openhub project scan` and `openhub project recommend` on Go, Express, NestJS, Unity, Unreal Engine and React + Spring fixtures, compared with v0.1.1.
- Full gates: tests, typecheck (including scripts), desktop build, `registry:validate`, `notices:check`, gitleaks, CI and CodeQL.

## Non-functional requirements

- Determinism: same input, same bytes.
- Safety: files are read, never executed; YAML parsing caps aliases and documents; evidence values are bounded and pattern-checked; regular expressions are linear (no new ReDoS patterns).
- Privacy: no network calls during analysis or recommendation.

## Out of scope for v0.2.0

- Automatic installation or updates without approval.
- Installing unverified discovery candidates.
- LLM-based detection or ranking.
- Installing editor plugins inside Unity or Unreal Engine.
- Code signing and a macOS release artifact.
- CLI translation.

## Open Questions
