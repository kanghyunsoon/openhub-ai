# Desktop Repair (v0.2.0 P0-3, PR A)

Part of [v0.2.0](v0.2.0.md). Brings the Core repair flow ([client-launcher-status.md](client-launcher-status.md), [kubernetes-tool-restriction.md](kubernetes-tool-restriction.md)) to the Desktop INSTALLED list. No Desktop-specific repair logic: the main process calls Core `planLifecycleRequest` (operation `repair`), `requestLifecycleApproval` and `runLifecycleTransaction`.

Labels: **Fact**, **Decision**, **Proposal**, **Open Question**.

## Flow (Decision)

INSTALLED list → problem state shown → **[복구 계획 확인]** → Core preview (same sentences as the CLI) → one checkbox per approval requirement → native confirmation dialog in the main process → repair → Health → result summary → status re-read.

- Button rule: the button exists only when Core can build a `ready` repair plan for that entry right now. The main process tries it while building the status (reads files and scans PATH only; no execution, no writes, no network). Candidate states: `tool-config-missing`, `tool-config-drift`, `tool-config-relocated`, `client-launcher-invalid`, and `config-drift` only when Core accepts it (OpenHub-managed paths only). Never for `untracked-foreign`, other config drift, unregistered servers, or when no verified Node.js installation is found (the warning shows the blocking code, for example `CLIENT_LAUNCHER_UNAVAILABLE`).
- One entry (client) per repair. Other clients in the same problem state keep their own button; nothing is repaired in bulk.
- Project scope only, as for every Desktop lifecycle action (D-003: Desktop does not read user-scope config). User-scope repair stays in the CLI; Core requires the `user-scope-config` approval for it.

## IPC and approval (Decision)

- New channel `lifecycle:plan-repair` in the existing pattern; execution uses the existing `lifecycle:run`. The renderer sends one state entry id (`scope:client:serverName`); paths, plans, digests and approvals sent by the renderer are ignored. The plan is kept in `LifecycleSession` in the main process and regenerated by Core right before execution (`PLAN_STALE` on any change).
- If another project was selected after the plan was made, `lifecycle:run` discards the plan without opening the dialog (`no-plan`). This also applies to update, rollback and Health (fix found while adding repair).
- The native dialog now lists everything the plan writes or runs, without paths: tool, each target (client, scope, file, entry replaced), the Node.js launcher change, preparation commands, the tool config action (create, replace, keep), Health, every plan warning, the approval requirements and the plan digest. Cancel writes nothing and runs nothing.

## Results (Decision)

The result view gains `outcome` and `summary`:

| Outcome | Core result | Meaning shown |
| --- | --- | --- |
| succeeded | `repaired` (also updated, rolled-back, health-checked, up-to-date) | completed |
| failed | `health-failed` (shown as HEALTH_FAILED), `config-failed`, `preparation-failed`, `state-commit-failed` | failed; this run's changes were reverted when compensated |
| partial | `rollback-failed` (`CONFIG_RESTORE_FAILED`) | some changed files could not be restored; external changes were not overwritten |
| not-run | `stale` (`PLAN_STALE`), `approval-required` | nothing executed; review the new plan and approve again |

Fixed guidance per code: `PLAN_STALE`, `CLIENT_LAUNCHER_UNAVAILABLE`, `TOOL_CONFIG_DRIFT`, `TOOL_CONFIG_STALE`, `CONFIG_DRIFT`, `CONFIG_RESTORE_FAILED`, `COMPENSATION_INCOMPLETE` (install-side code, kept for consistency), `MANUAL_SETUP_REQUIRED`. A Health failure is never shown as success.

## Verification (Fact, 2026-10-10)

- `apps/desktop/test/repair.test.ts` (14 tests): kubernetes-mcp-server installed by Core into a temporary project, then the Desktop IPC handlers are called. Healthy state has no button and the repair channel refuses (also user-scope ids, foreign ids, paths, non-strings); tool config deleted and changed; Windows Node.js moved (in-memory Windows file system); project copied (relocated); preview and full dialog content without absolute paths; cancel (no npm call, no Health, files and Version State byte-identical); file changed right after approval (`PLAN_STALE`, not-run); Health failure (HEALTH_FAILED, files restored, Version State unchanged); external change during compensation (partial, `CONFIG_RESTORE_FAILED`, external content kept); other MCP entries preserved; user-scope repair plan needs `user-scope-config` and the dialog shows it; project switched after planning (no dialog, nothing written); Core-refused config drift and missing Node.js (no button, blocking code shown); renderer and preload wiring.
- Existing Desktop lifecycle tests (update, rollback, Health) pass unchanged.
- Real Electron E2E (`apps/desktop/test/repair-electron.e2e.test.ts`, `OPENHUB_E2E=1`, Windows, Electron 44.5.1): the real app is started with `--smoke` and `OPENHUB_SMOKE_REPAIR` on a project prepared by Core with a deleted tool config. The renderer clicks through the real button, checkboxes and confirm button; the call crosses preload and main IPC; the dialog is the smoke auto-confirm. Result: `repaired`, outcome succeeded, one dialog ("OpenHub 복구 승인"), Health run once, status afterwards `state-consistent` for all three clients, tool config recreated. Smoke-only fakes: npm cache entries (no network), Health. The existing install/update/release/DISCOVER Electron smoke also passes.
