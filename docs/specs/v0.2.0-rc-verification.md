## RC run rules (Decision)

- Use the artifacts of one `release.yml` dry run (`dry_run=true`, `publish=false`) of one pinned main commit. Record commit SHA, run ID, file name, SHA256, size, platform and test environment for each artifact.
- Isolated environment only: a disposable VM, a disposable CI runner, or a separate OS user / isolated home and app-data folders. Never the maintainer's own profile, clients, credentials, clusters or databases.
- Synthetic projects, a synthetic Kubernetes API and fake credentials only. Real npm with a separate cache.
- Each step gets **PASS**, **FAIL** or **NOT-RUN** per OS. A step is PASS only if it was performed with the packaged app on that OS and its check passed. Anything not performed is NOT-RUN, never PASS. A failure blocks the RC.
- The Windows unsigned-installer warning (SmartScreen / Smart App Control) is recorded, not suppressed.

### Automated verdict (Decision)

The packaged-app harness (`scripts/rc/packaged-rc.mjs`, workflow `rc-packaged.yml`) is fail-closed. It writes the result JSON first, then exits with the verdict of `scripts/rc/check-rc-result.mjs`; the workflow runs the same check again as a separate step, so a missing result file also fails the job. Steps 1, 2 and 15 are workflow steps that fail on their own.

- Steps 3–14 must each be PASS. A FAIL step or check, a recorded error, a missing step, an unknown status or a NOT-RUN step fails the run.
- Sub-items that cannot be performed are recorded as structured NOT-RUN entries (`{ id, step, detail }`). Only these are allowed, and each is printed in the verdict:

  | id | Step | OS | Reason |
  |---|---|---|---|
  | `korean-os-first-start` | 3 | Windows | The runner's OS display language cannot be switched (Linux checks it via `LANG`). |
  | `exact-version-v1-v2-v1` | 9 | Windows, Linux | The packaged app has no exact-version choice yet (option A, separate PR). |
  | `health-failure-compensation` | 11 | Windows, Linux | Needs a failing real MCP server in the packaged app; covered by automated tests only. |

  Any other NOT-RUN fails the run. Adding an entry needs a reason here; entries are removed when the sub-step becomes runnable.
- `inject_failure` (workflow_dispatch) forces a failure to prove the job fails; an injected result never passes.

### Step 15 per OS

- **Windows:** run the NSIS uninstaller (Apps & features or the uninstaller in the install folder). Before and after, compare byte for byte: the client files OpenHub wrote (`.mcp.json`, `.cursor/mcp.json`, `.codex/config.toml`, `~/.cursor/mcp.json`, `~/.codex/config.toml`), the user's other MCP entries, and `~/.openhub/state/lifecycle.json` with `~/.openhub/tool-config/`. Expected: the uninstaller removes the program only; it does not touch client configuration or `~/.openhub`. Record what remains in the app-data folder.
- **Linux:** an AppImage has no uninstaller. Removal means deleting the AppImage file (and any desktop entry the user created). Run the same byte comparison before and after. Expected: nothing else changes.
- Each OS gets its own PASS / FAIL / NOT-RUN.

### Version change in the packaged app (steps 9 and 10)

Fact: the packaged app uses the bundled Registry, and its Update has no version input; it resolves the Manifest's own spec. The bundled `memory-mcp` Manifest is unpinned (`npx -y @modelcontextprotocol/server-memory`), Kubernetes and MongoDB are pinned to one reviewed version (update reports up to date).

- What the packaged app can show today, and the RC runs: install memory-mcp (unpinned, launch-on-demand) → Update (resolves the npm `latest` dist-tag to an exact version, Prepare, Health, state commit) → Rollback (returns to the previous, unpinned entry; the app says exact artifact is not guaranteed) → Health. Check that the client entry and Version State change exactly as shown.
- What it cannot show: an exact V1 → V2 → V1 change. That would need a pinned V1 Manifest in the bundled Registry or a version choice in the app. The RC does **not** edit the Registry, does **not** inject a test Registry into the artifact, and does **not** change the user's existing MCP entries to force it. This sub-step is **NOT-RUN** in the packaged app; the Core real-npm E2E stays separate evidence and does not replace it. A design for an explicit, approved way to test it is proposed in a separate draft pull request.

## Exit criteria

Every step is PASS on both Windows and Linux (the exact V1 → V2 → V1 sub-step may stay NOT-RUN only if the release decision accepts it); no new CodeQL alert; `desktop-e2e`, `check`, `codeql`, `secret-scan` green on the RC commit; release notes state the Cursor, macOS and Kubernetes limits.

## Remaining English gaps relevant to the RC (Fact)

- Approval dialogs (install, lifecycle, Adopt, Benchmark) are built from plan structure in English; no approval information is dropped.
- Pinokio: the Desktop only previews plans; approval and execution happen in the CLI, which is Korean-only. The Desktop preview shows Pinokio notices as `[code] Korean text` although the notices carry codes. Proposal: English notice sentences by code.
- Manifest summaries are authored Korean text (display only). Release impact reasons show codes with levels. Recommendation reasons are generic per code, without names or numbers. None of these is shown in an approval dialog.
